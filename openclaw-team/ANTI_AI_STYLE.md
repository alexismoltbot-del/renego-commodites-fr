# ANTI_AI_STYLE.md

Shared writing contract for OpenClaw deliverables.

Read this before writing:

- handoffs
- reports
- landing copy
- PM syntheses
- any public-facing or decision-facing prose

## Goal

Make the writing sound specific, credible, and human.
Kill the generic "AI assistant" tone.

## Priority Order

Apply rules in this order:

1. truth
2. sources and dates
3. product and legal constraints
4. clarity
5. style

If style conflicts with accuracy, style loses.

## What To Avoid

- throat-clearing openers
- fake enthusiasm
- vague consultant language
- bloated transitions
- generic "3 takeaways" framing when the concrete answer is obvious
- inflated certainty
- copy that hides the real risk

Avoid phrases like:

- "Great question"
- "I'd be happy to help"
- "In today's fast-paced landscape"
- "It's important to note"
- "seamless"
- "robust"
- "revolutionary"
- "best-in-class"
- "leveraging AI"
- "unlock value"

## What Good Looks Like

- lead with the fact, blocker, decision, or recommendation
- use numbers, dates, file names, and named risks
- keep sentences short unless detail really helps
- prefer plain words over abstract words
- let the text sound earned, not polished for its own sake
- state uncertainty directly
- end with the next action or open decision when relevant

## Default Tone

- calm
- precise
- slightly opinionated when earned
- honest about tradeoffs
- never salesy unless the task is explicitly marketing copy

## By Document Type

### Handoffs

- first line = what changed or what is blocked
- include exact files to read
- name the remaining risk explicitly

### QA Reports

- findings first
- severity explicit
- no softening language around real regressions

### Landing Copy

- one narrow promise
- no claim without proof in product or sources
- concrete beats clever

## Quick Rewrite Test

Before shipping, ask:

- Could this have been written by any generic AI tool?
- Did I name the real file, date, price, bug, or approval?
- Can I cut the first sentence and improve the text?
- Did I say something true and useful, or just well-shaped?

If the answer is bad, rewrite.

## Examples

Bad:

> In today's rapidly evolving market, users need smarter and more seamless ways to optimize recurring expenses.

Better:

> ReneGo compares your current box invoice against dated market offers and tells you to keep, renegotiate, or switch.

Bad:

> This issue may potentially create some inconsistency that should be monitored carefully.

Better:

> BUG-11 is still open: Red is 24,99 EUR in code and 22,99 EUR in the landing copy.

Bad:

> Here are three key takeaways to consider moving forward.

Better:

> The only blocker left is source alignment between code and public copy.
